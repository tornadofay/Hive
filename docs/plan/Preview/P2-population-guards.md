# Preview — Autonomous Population & Two-Level Guards [Target]

Objective: implement governed autonomous specialist creation with two-level guards (absolute ceilings + configurable operating limits) and atomic admission/reservation.

Governing Hive identity and lifecycle (scope anchor):
- The standalone Workbench owns exactly one persistent governing Hive for the installation/profile (not one per run or session). That Hive has a stable persistent identity (Hive id) that survives application restart and is reused across runs/sessions.
- Every task/run references that governing Hive identity; limits, counters, reservations, and guard evidence are always keyed to it and never span unrelated Hives.
- A new governing Hive is created only through an authorized management action (initial onboarding or explicit archive/reset). Creating a fresh Hive per session is not permitted, because it would silently reset lifetime allowances and split the persistent specialist catalog.
- Lifecycle: a governing Hive may be archived or reset only through an authorized management action; archiving/resetting establishes a fresh allowance as specified below and is recorded as evidence. Archiving/resetting preserves prior audit evidence (guard decisions, configuration changes, run records) by reference; it establishes a new allowance but does not delete historical evidence. Dormancy does not reset any allowance.
- If independent Hives per session were ever required, lifetime limits would need a separate cross-session scope in addition; the default and required behavior is the single persistent governing Hive above.

Absolute ceilings (concrete, non-toggleable) — proposed values, subject to developer confirmation. These are not a finalized implementation contract until explicitly approved or revised; approval or revision is a pre-implementation gate. Do not silently treat the proposed numbers as final.
- Max recursion depth: governing Hive = depth 0. Permitted specialist depths: 1, 2, 3. A creation that would place a specialist at depth 4 is rejected. Scope: per creation chain; reset: n/a (structural).
- Max creation rate: 10 specialists per 60-second sliding window. Scope: per governing Hive instance. Counter tracks creation attempts admitted to the creation pipeline (including those later dedup-resolved), so the limit cannot be bypassed by spamming duplicates. Rejected attempts that never pass initial validation are not counted. Reset: window slides; no manual reset.
- Max creation count (lifetime): 256 specialists per governing Hive instance (includes dormant). Scope: per Hive lifetime; counter survives application restart via persisted state. Reset only on explicit authorized Hive archive/reset, which establishes a fresh allowance; dormancy does not reset it. Archiving/resetting requires the same authorization as other destructive management actions and is recorded as evidence.
- Max creation count (per task): effective task cap = min(configured task population cap, effective persistent membership allowance). Scope: per task run. Reset: end of task.
- Authorization enforcement, sandbox, secret redaction, process termination, exact duplicate prevention, provider/platform quotas: hard floors; not numeric.
- Task population vs. membership: the effective task cap can never exceed the available membership allowance (min(configured task cap, effective membership cap)). Configurable caps are always ≤ the corresponding absolute ceiling; Settings may lower but never raise above the ceiling.

Scope:
- Relationship to configurable limits: configurable caps (membership 4–64, task population 1–16, concurrent 1–8) are always ≤ the corresponding absolute ceiling; Settings may lower but never raise above the ceiling. Disabling a configurable restriction never disables its enforcement mechanism.
- configurable operating limits bounded by ceilings: persistent membership cap (default 12, 4–64), task population cap (default 6, 1–16), concurrent execution cap (default 4, 1–8), duplicate strictness (semantic threshold), per-run budget cap (tokens+cost, shared current usage), dormancy policy, consequential-action approval, creation-log visibility;
- atomic admission/reservation for concurrency; immutable effective policy snapshot per run; Settings changes apply to new runs only;
- per-run policy snapshot captures operating policy (limits/preferences) only. Live enforcement is never snapshotted: current authorization, credential validity, cancellation, emergency stop, and hard safety requirements are evaluated on every consequential action. A snapshot must never grant authority that has since been revoked.
- concurrent specialty creation dedups at the catalog boundary;
- reversible dormancy instead of destructive auto-retirement; dormancy retains the Preview 1 retained state (AgentDefinition + specialty profile, configuration, assignment history, produced artifacts, and explicitly persisted working context) and does NOT retain CognitiveAgent-style learning, evaluation, adaptation, or experience-based strategy revision (reserved for Phase 4).
- guard decisions recorded as attributable evidence.

Budget enforcement (atomic):
- Shared budget reservation: before any concurrent specialist work begins, reserve the estimated token/cost against a shared budget ledger keyed by run; admission fails closed when the reservation would exceed the per-run cap or provider/platform quota.
- Reconciliation: on completion, reconcile the reservation against actual provider-reported usage; refund unused reservation; charge overage against the run (and surface it) when actual exceeds estimate.
- Separate limits: a token limit (tokens) and a monetary limit (cost in the configured currency unit); each has its own reservation and reconciliation rule; exceeding either fails closed.
- Reservation identity and restart safety: reservations carry a stable reservation id, run id, governing Hive id, estimate basis, and timestamps; reconciliation is idempotent by reservation id (no double-settlement after restart).
- Uncertain provider outcomes: distinguish (a) a request confirmed not to have been submitted (release the reservation) from (b) a request submitted with an unknown outcome (retain a conservative reservation until reconciliation; release only the portion known to be unused). A locally cancelled or timed-out call may still have reached the provider and incurred cost.
- Terminal policy for unresolved reservations (budget-reservation lifecycle, distinct from run lifecycle): a reservation for an unknown-outcome request enters `Reconciling` status within the budget ledger while the owning run keeps its current run state. Run terminal states are not changed by budget reconciliation: an already-`Completed`/`Cancelled`/`Failed` run remains in that state; unresolved budget is recorded as a separate financial/verification status on the run (e.g., `BudgetStatus: Reconciling` → `Settled-as-spent`/`Waived`) with evidence. Reconciliation is retried on a bounded schedule: immediate, then 1 min, 5 min, 15 min, 1 h, 6 h, and a final attempt at 24 h (proposed values, subject to developer confirmation). If reconciliation cannot complete within the 24-hour reconciliation window, the reservation is conservatively settled as spent (charged to the run) and transitions to `Settled-as-spent`; if the run is in a non-terminal state it is then marked `Failed — budget unresolved`. Waiver governance: only an authorized actor (a user or manager with budget authority, not the application developer as an implicit runtime authority) may waive, with a recorded rationale and evidence; a waiver on a non-terminal run transitions it to `Completed with accepted verification exception` and retains the charge; a waiver on an already-terminal run only updates `BudgetStatus` to `Waived` and records evidence (it never erases an actual or potentially incurred charge and never changes the run's terminal state). Operator intervention (authorized management action) may also re-open reconciliation as a financial adjustment; reopening affects only the budget ledger and does not move a terminal run back to a non-terminal state. An unresolved reservation is never held indefinitely and never silently released as unused.
- Run↔budget transition table: (run state, reservation status) → allowed outcome: (any non-terminal, Reconciling) → run continues; reconciliation completes → (Completed, Settled) or (Failed, Settled-as-spent). (Completed/Cancelled/Failed, Reconciling) → run stays terminal; budget may move Reconciling→Settled/Settled-as-spent/Waived without changing run state. (Failed — budget unresolved, Reconciling) → waiver → (Completed with accepted verification exception, Waived) with charge retained. Recovery from `Cancelling` always settles to `Cancelled`; it never resumes execution. Recovery from `Paused` reconciles but keeps the run `Paused`. Automatic recovery never auto-resumes a paused run.
- Worst-case estimate: when the selected provider has no usable pricing information, use a defined fail-closed outcome — deny admission rather than allow an unbounded charge. "Worst case" is only enforceable with a defined bound; absent one, admission is denied.
- Over-budget result: blocks further admissions and stops additional work for the run when appropriate; surfaces the overage.
- Edge cases / release invariant: release a reservation when submission is confirmed not to have occurred, or release only the portion confirmed unused. Retain the reservation for any submitted request with an unknown outcome. Settle unresolved reservations under the explicit terminal policy (below) without silently refunding them. Cancellation, timeouts, and process restart follow this invariant; duplicate settlement is idempotent. Verification must assert this under cancellation, timeouts, process restart, and duplicate settlement.
- Disabled soft cap: disabling the configurable per-run budget cap disables only that soft cap. Provider/platform quotas and all mandatory hard limits (absolute ceilings, authorization, sandbox, secret redaction, process termination) remain enforced; a run with the soft cap disabled still cannot exceed provider/platform quotas or any hard ceiling. The hard limits are never configurable off.
- Mapping to Phase 1.30: the preview's shared per-run budget maps to the planned per-runtime budget boundary in `docs/plan/Phase1/1.30.md` (a plan, not a completed implementation); the preview extends it with multi-Agent sharing and reservation semantics rather than introducing a second budget scope. Implementation of the underlying budget mechanism remains governed by Phase 1.30.

Verify:
- concurrent requests do not exceed concurrent cap;
- effective task cap never exceeds available membership allowance;
- failed/interrupted runs do not double-release or permanently hold a reservation; uncertain outcomes retain a conservative reservation;
- Settings change mid-run does not alter in-flight authority, but revocation/cancellation/emergency stop take effect immediately;
- two concurrent identical creation requests yield one specialist;
- exact duplicate never possible regardless of strictness setting;
- dormancy preserves the Preview 1 retained state (AgentDefinition + specialty profile, configuration, assignment history, produced artifacts, and explicitly persisted working context) and is reversible; it does not retain CognitiveAgent-style learning, evaluation, adaptation, or experience-based strategy revision (reserved for Phase 4).
- guard decisions and configuration changes recorded as attributable evidence (actor, time, previous and new values, affected scope, applicable policy profile);
- "creation-log visibility" changes presentation only and never disables recording of guard evidence.
- SQL Server and Embedded parity for guard/policy persistence where applicable.
