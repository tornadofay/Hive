# Preview — End-to-End Coordinated Run (Manager / Hive / Specialists) [Target]

Objective: define the complete preview-only orchestration flow that lets the Workbench complete a substantial user request through coordinated Agents, reusing existing `Hive.Management` and MAF boundaries. This plan must not create a second coordination engine.

Scope:
- A user request becomes a durable task/run owned by the governing Hive instance and its Manager; the Manager is the single coordination owner.
- Manager decomposition: the Manager breaks the request into sub-tasks, assigns existing specialists or requests governed creation (P2), and coordinates concurrent work through MAF-owned orchestration primitives (no Hive-side second engine).
- Critic participation: a critic role reviews intermediate results before finalization and the final result before completion; the Manager combines results and determines completion against the request's success criteria. Mandatory enforcement failures (authorization denials, revoked permissions, hard safety requirements, project-scope restrictions, mandatory guard failures) are non-waivable: they block completion and cannot be accepted or overridden by the Manager or critic. Acceptance applies only to known, non-prohibited limitations (a correctness or quality limitation that policy permits an authorized actor to accept); such acceptance requires an authorized actor (user or manager with the relevant authority), applicable policy permission, and explicit recording. Stylistic or optional improvements do not block. Disagreement between Manager and critic is resolved by the Manager with the rationale and both positions recorded as evidence; that decision cannot alter the outcome of a separately enforced authorization or safety check.
- Pause/stop/cancellation/failure/restart: define propagation to all participating Agents, reservation release (P2), and durable recovery of run state; application restart resumes or fails the run deterministically.
- Correlation: conversation history, specialist activity, generated files, and final artifacts are correlated to the run via durable identifiers; evidence recorded per guard decisions (P2) and configuration changes.
- WorkItem binding (decided): the coordinated run reuses the WorkItem identity as its run identity — there is no separate durable run aggregate. The WorkItem (per `v1-host-and-management.md`) is the authoritative durable user-visible work aggregate and holds run state, assignments, artifact index, and reservation references. Run assignments and artifacts reference that same identity. No overlapping durable task identities or duplicate status histories are permitted; the Workbench exposes one authoritative user-visible work status and history.
- WorkItem status mapping (no second authoritative history; no WorkItemStatus enum change): coordination states map onto the existing WorkItem status and resource lifecycle as follows: `Created` -> WorkItem `Created`; `Planning`/queued work -> WorkItem `Queued`; `Running` -> WorkItem `Running`; `Paused` -> WorkItem `Running` with `ResourceLifecycle.Suspended` (existing `Suspend`/`Resume`), recorded via metadata `CoordinationState=Paused`; `Cancelling` -> WorkItem `Running` with metadata `CoordinationState=Cancelling` (transient, settles to `Cancelled`); `Recovering` is not persisted (on restart any non-terminal WorkItem is recovered in memory; persisted status remains its prior value); `Completed with accepted verification exception` -> WorkItem `Completed` with metadata/attachment `VerificationExceptionAccepted=true`; `Failed -- budget unresolved` -> WorkItem `Failed` with metadata `BudgetStatus=Settled-as-spent` (or unresolved). `PendingApproval` maps to approval-gated tool/operation state, not a run state. `Rejected` is not produced by the coordinated run. This preserves existing SQL Server/Embedded persistence and migration compatibility: no new persisted status values; coordination-only state lives in metadata/attachment and resource lifecycle.
- Reuse boundaries: Hive.Management owns management/application operations; MAF owns orchestration mechanics; Hive.Host.WinForms does not bypass Management; no host business state in Hive persistence.
- Persistence: authoritative run state, assignments, artifact index, and reservation references are persisted in the existing Hive persistence boundary (Embedded/SQL Server parity per P1) under the governing Hive identity; host business state remains host-owned and is not stored in Hive persistence. Recovery reads these records; no in-memory-only run state is authoritative.

Durable run lifecycle:
- Run states (run lifecycle, owned by P5; budget-reservation status is a separate ledger lifecycle owned by P2): `Created` → `Planning` → `Running` → `Paused` | `Cancelling` | `Completed` | `Completed with accepted verification exception` | `Cancelled` | `Failed` | `Recovering`. Terminal states: `Completed`, `Completed with accepted verification exception`, `Cancelled`, `Failed`. `Paused` is non-terminal and is preserved across restart.
- Transitions are explicit and recorded with actor, time, and reason. `Paused` resumes to `Running` only on explicit resume; `Cancelling` settles to `Cancelled`; `Recovering` resolves to `Running` or `Failed` (never to `Running` from a previously `Paused` run).
- Assignment/recovery: each sub-task assignment carries a durable assignment id, specialist id, and run id. On restart, assignments in `Running`/`Paused` are re-evaluated: idempotent sub-tasks resume; non-idempotent or ambiguous sub-tasks fail closed and are re-planned by the Manager. No sub-task is silently re-run without reconciliation.
- Partially completed work: completed sub-tasks are not repeated; their artifacts are reconciled against the run's durable artifact index. Reservations for unresolved provider outcomes follow P2's terminal policy.
- Restart behavior: on application start, any run not in a terminal state enters `Recovering` and is resolved deterministically. A run that was `Paused` is reconciled (reservations, assignments) but remains `Paused` until explicitly resumed; automatic recovery never auto-resumes. A run that was `Cancelling` completes cancellation and settles to `Cancelled`; it never resumes execution. A run that was `Running`/etc. resumes or fails closed with a recorded reason. No automatic destructive action occurs.

Verify:
- a substantial request completes end-to-end through coordinated specialists in the Example host;
- the same scenario completes end-to-end in the standalone Workbench, exercising its own composition and onboarding;
- pause/stop/cancellation propagate and leave no untracked executions or assignments; specialists become dormant rather than destroyed;
- restart recovers run state deterministically (resume or fail-closed);
- no second coordination engine introduced (orchestration delegated to MAF).
