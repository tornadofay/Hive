# 1.3 — OpenAI-compatible Provider Adapter

## Purpose

Provide one shared OpenAI-compatible transport implementation that can serve compatible hosted and local providers through configuration rather than creating one adapter per vendor.

## Scope

- Parameterize the adapter by base URL/endpoint and authorized credential context.
- Map Hive execution requests to the OpenAI-compatible HTTP contract and normalize responses/errors into Hive's provider boundary.
- Preserve the Provider → ProviderAccount → ExecutionTarget resource separation.
- Keep provider transport concerns inside Hive.Providers.OpenAICompatible.
- Respect the existing cancellation, timeout, structured-error, and secret-redaction boundaries.
- Support compatible hosted and local endpoints through configuration of the same adapter.

## Architecture boundary

The adapter owns transport/protocol translation. Hive.Management owns provider configuration and credential resolution; Hive's execution-planning boundary selects the target; MAF owns execution mechanics where applicable.

Adding another OpenAI-compatible provider should normally be configuration, not another transport implementation.

## Non-goals

No second provider transport architecture, vendor-specific orchestration engine, secret persistence, or direct host-business integration belongs here.

## Verify

Use deterministic local fake-server coverage for successful responses, malformed responses, timeout, cancellation, authentication failure, rate limiting, transport failures, and structured-output failures. Verify secrets never appear in requests captured by tests, diagnostics, or normalized error output.
