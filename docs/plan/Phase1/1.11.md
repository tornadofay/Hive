# 1.11 — Initial Workspace & WorkItem Operations

## Purpose

Establish the initial Workspace foundation over Hive.Management for image-backed WorkItems, operational status, and the first human interaction with governed approval state.

## Scope

- Submit or attach an image to a WorkItem through the existing image-submission boundary.
- Show WorkItem lifecycle/status and relevant activity.
- Show relevant execution/provider operational status already exposed by Hive.Management.
- Surface WorkItem notifications/state changes required by the initial Workspace experience.
- Display an existing PendingApproval state when a consequential operation requires human authorization.
- Allow Approve / Reject through the existing authoritative approval/intervention contract.
- Preserve WorkItem identity, ownership, scope, provenance, and stale-state protection.
- Keep the initial Workspace single-Agent and independent of Hive membership or Swarm state.

The approval interaction is a consumer concern in this slice. The generalized Tool/policy/permission and human-intervention architecture is established by the later governance slice; 1.11 must not create a parallel approval model.

## Architecture boundary

The Workspace is a presentation/control surface over Hive.Management. It does not perform direct persistence, provider calls, host-business writes, or authorization decisions.

The Workspace reads authoritative WorkItem and approval state and submits the corresponding Management operation for Approve/Reject. A stale approval or unauthorized transition is rejected by the owning boundary rather than trusted because the UI displayed the action.

The initial workspace may demonstrate the approval lifecycle without owning the later governed business-operation pipeline. Actual consequential host write execution remains in the later business-operation slices.

## Non-goals

No direct LLM chat, Agent assignment UI for multiple Agents, persistent Hive membership, Swarm state, host-business mutation, second authorization system, or provider transport implementation is introduced here.

## Verify

Verify that image submission creates or updates the correct WorkItem; status/activity and relevant execution/provider state are displayed from authoritative sources; PendingApproval is rendered correctly; Approve/Reject changes authoritative state only through the owning boundary; stale or duplicate approval actions are rejected; failures are surfaced without creating divergent UI-only state; and the Workspace creates no hidden Hive/Swarm behavior.
