# 1.7 — Event Log, Snapshots & Transactional Outbox

## Purpose

Establish Hive's durable event/snapshot/outbox boundary for state transitions that must be persisted atomically and later replayed deterministically.

## Scope

- Append durable domain events rather than replacing history with mutable snapshots.
- Fold supported events into snapshots for efficient recovery.
- Persist the event, updated snapshot, and applicable outbox work in one transaction.
- Preserve event type, payload schema version, correlation/causation identity, resource identity, and ordering information from the Phase 0 event foundation.
- Keep snapshots as recovery aids rather than the authoritative replacement for event history.
- Ensure failed transactions cannot leave an event without its corresponding state transition or outbox work.

## Architecture boundary

Hive owns durable event/snapshot/outbox semantics. Hive.Persistence owns the storage implementation; application/domain owners define the state transitions and event contracts. The outbox exists to continue committed work after the transaction completes and is never the source of truth for the already-committed state change.

## Non-goals

No second event store, external message-bus dependency, or alternative orchestration engine is introduced in this slice.

## Verify

Verify successful atomic persistence, transaction rollback across event/snapshot/outbox state, deterministic snapshot folding and replay of supported events, schema-version handling, correlation/causation preservation, and recovery from incomplete or failed persistence operations.
