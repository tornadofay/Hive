# 1.31 — Bounded Base-Agent Problem-Solving Loop

## Purpose

Make model reasoning useful for difficult normal-Agent tasks by adding a bounded, task-scoped loop for candidate attempts, observable progress assessment, method changes, challenge, and applicable verification. This is a Base-Agent capability; it does not create a CognitiveAgent or make persistent cognition a prerequisite for V1.

## Scope

- Establish task-provided success criteria, constraints, relevant context, and an explicit attempt/time/token/cost/concurrency budget before starting iterative work.
- Support a direct one-attempt path so simple tasks do not incur unnecessary extra model calls.
- Record scoped attempt/candidate evidence under the owning WorkItem, Execution, or explicit problem-solving operation. Preserve method/approach summary, candidate result, material assumptions, predecessor references, evidence/check references, observed progress, reason for retry/switch, status, and applicable time/cost evidence.
- Distinguish a retry of substantially the same method from a materially different approach, decomposition, algorithm, tool/evidence path, model configuration, or specialist request.
- Assess progress from observable output/evidence changes where possible. Model self-assessment may contribute but is not authoritative by itself. Detect bounded stagnation and choose a different method, seek necessary information, verify, stop, or report unresolved status.
- Allow a bounded critique/challenge pass to seek counterexamples, contradictions, unsupported assumptions, unhandled conditions, or simpler alternatives. Preserve challenge results as evidence; do not make critique an automatic rejection/approval.
- Reuse existing deterministic tests, validation, and authorized Tools to verify a candidate when applicable. Scope every check to the exact candidate/input/artifact and check configuration; distinguish self-critique from an independent verifier.
- Enforce cancellation, stale-state checks, attempt bounds, budgets, concurrency limits, and deterministic terminal behavior. Report the strongest supported candidate and remaining uncertainty when success cannot be established.
- Use provider/model reasoning controls only where existing capability evidence and adapter contracts support them; preserve safe behavior when support is Unknown or Unsupported.

## Architecture boundary

The loop coordinates the current task; it does not autonomously learn or promote durable strategy. It reuses the existing provider/model capability, Execution Planner, WorkItem/Execution, Tool, persistence/event, resource-control, and Microsoft Agent Framework (MAF) boundaries. MAF continues to own framework execution/orchestration wherever it provides the required mechanism; Hive adds only bounded problem-solving policy/state that MAF does not own.

Attempts are task-scoped evidence, not a second global Resource model. Do not persist raw hidden chain-of-thought as required state. Persist concise approach summaries, decisions, outputs, evidence references, switch reasons, verification details, and relevant provenance instead.

## Non-goals

- No changes to or prerequisites for the existing V1 business-app approval/write/receipt/Review pipeline.
- No autonomous persistent strategy learning, CognitiveAgent state, Dreams, or Learning Candidate promotion.
- No universal verification platform or mathematics-specific subsystem.
- No parallel implementation of an orchestration engine alongside MAF.
- No unbounded attempts, mandatory multi-Agent execution, or mandatory extra calls for every task.
- No use of model confidence or model self-report as authorization, objective verification, or proof of progress.

## Verify

- A simple task can complete in one attempt without unnecessary additional calls.
- Iteration can refine a candidate after a concrete failure and can switch to a materially different method.
- Repeated near-identical attempts are not misrepresented as independent approaches.
- Progress, stagnation, contradiction, and unresolved outcomes remain distinguishable with observable evidence.
- Critique can surface a concrete weakness without becoming an authoritative verdict.
- Independent verifier results identify the exact checked candidate/input/configuration and remain distinct from model self-critique.
- Candidate/attempt evidence preserves owner, scope, provenance, correlation, predecessor links, and actual-versus-simulated distinction where applicable.
- Attempt/time/token/cost/concurrency limits, cancellation, stale-state rejection, provider capability handling, and deterministic stop conditions are exercised.
- Existing authorization, immutable execution snapshot, V1 approval/receipt/Review behavior, and SQL Server/Embedded backend-neutral boundaries remain unchanged.
- The capability has an Example Host scenario using public contracts and deterministic fixtures.
