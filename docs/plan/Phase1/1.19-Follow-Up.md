# 1.19A — Execution Target Preferences & Favorite Target Pool

## Objective

Add a durable, owner/scope-aware favorite ExecutionTarget set that acts only as an optional candidate-pool filter for future target selection consumers.

The feature does not introduce another selection mode. The existing capability-aware ExecutionTargetSelector remains authoritative for capability qualification, ranking, and Auto / Preferred / Fixed semantics.

## Scope

### Durable preference

- Store favorite ExecutionTargetId values as user/scope preference state, separate from ExecutionTarget resource configuration.
- Preserve favorite references when a target is retired so the durable preference can become effective again if the same target is reactivated.
- Save operations validate that every referenced target belongs to the caller's authorized resource view.
- Empty favorite state is valid and means no filtering.
- Duplicate favorite identities are rejected deterministically.
- Favorite ordering is presentation state only; it must not become a ranking signal.

### Candidate filtering

All supplied ExecutionTargets
        ↓
Favorite filter (only when non-empty)
        ↓
Existing capability / lifecycle qualification
        ↓
Existing Auto / Preferred / Fixed selection

Rules:
- no favorites → return the supplied candidates unchanged;
- non-empty favorites → return only targets whose durable IDs are in the favorite set;
- filtering must not mutate targets;
- filtering must not mutate capability state;
- filtering must not bypass authorization;
- filtering must not silently fall back to non-favorites;
- the existing selector still rejects inactive targets and applies capability requirements;
- Preferred remains one preferred target with fallback;
- Fixed remains one exact target with no fallback;
- favorite ordering never changes selector ranking.

### Provider Settings UI

Normal Settings → Providers becomes a two-page tab surface:

Providers
├── Providers                 ← existing page
└── Favorite Execution Targets

The first page retains the existing Provider CRUD, Refresh, and Advanced behavior.

The second page is a simple favorite-preference CRUD surface:
- lists only the ExecutionTargets currently saved as favorites;
- provides Add Favorite, Remove, and Refresh actions;
- does not show a catalog of every ExecutionTarget and does not place Provider / Account filters on the main Favorites page;
- Add Favorite opens a compact picker with Provider → Account → Execution Target selectors;
- Provider and Account are used only to narrow the available target choices in that Add picker;
- adding and removing a favorite persist immediately through Hive.Management;
- reports save/load errors through the existing Hive UI error/output boundaries;
- does not expose secrets or provider transport operations.

## Scope boundary

AgentDefinition and other ExecutionTarget selection UIs are outside this slice. This slice only creates and manages the durable favorite list. Existing Agent target behavior remains unchanged until its owning phase defines how Auto, favorites, and explicit target selection interact.

## Ownership

- Hive.Core owns the reusable candidate-filter semantics.
- Hive.Management owns favorite preference validation and application-facing operations.
- Hive.Persistence owns durable SQL storage and migration.
- Hive.Host.WinForms owns the Provider Settings and target-selection presentation.
- Hive.Example.WinForms demonstrates the real Settings surface; it does not create a competing favorite store.

## Security and lifecycle

- Favorite state is never an authorization grant.
- Favoriting a target does not activate it, modify capabilities, bypass provider/account lifecycle, or expose credentials.
- A favorite pointing to a retired target remains stored, but a retired target cannot qualify for actual execution through the existing selector.
- Save requests reject target IDs outside the caller's accessible scope.
- UI only receives safe target metadata and never secret material.

## Persistence model

Use a dedicated preference table keyed by:
- DeploymentId;
- OwnerPrincipalId;
- explicit preference ScopeKind / ScopeIdentity;
- ExecutionTargetId;
- deterministic presentation order.

The preference scope follows Hive's canonical resource-scope rules. User-scoped preference state requires the applicable tenant and user identities; tenant-scoped state requires the tenant identity. Missing required scope identity must fail closed rather than implicitly broadening the preference to Global or another broader scope.

The row references the durable target identity and is not itself a Hive resource.

## Verification

Focused coverage must prove:
- empty favorites preserve current candidate behavior;
- non-empty favorites filter candidate IDs exactly;
- filtering does not change target objects or capability state;
- duplicate IDs are rejected;
- inaccessible target IDs are rejected;
- scope isolation is enforced;
- favorites persist and reload;
- retired favorites remain stored;
- favorite order does not affect selection ranking;
- Provider Settings renders the two-tab structure;
- the Favorites page lists only saved favorites and exposes Add / Remove / Refresh actions;
- the Add Favorite picker narrows target choices through Provider and Account selectors;
- no Agent target-selection UI changes are required in this slice;
- UI save failures are surfaced through existing Hive error handling.
