# 1.18A — Embedded Persistence Profile
Objective: add the Embedded Persistence Profile, catch it up to the **current SQL Server-backed Hive persistence surface**, preserve the existing SQL Server backend, and provide complete bidirectional migration of all Hive-owned durable data between SQL Server and Embedded.

**Implementation structure:** 1.18A is one roadmap phase containing **six sequential implementation slices**. Each slice has its own bounded implementation/verification gate, and the next slice must not begin until the previous slice has been developer-verified. These are internal slices of 1.18A, not additional roadmap phases.

## Why this phase exists

Hive's current persistence implementation is SQL Server-specific. That remains appropriate for server/serious deployments, but a normal desktop installation should be able to run Hive without first installing or administering a database server.

This phase therefore adds an Embedded Persistence Profile as a second deployment backend. SQL Server remains supported and is not reimplemented. The Embedded backend is the catch-up implementation for the durable persistence surface that exists in the repository when 1.18A starts. This is a persistence/deployment capability, not a new domain model and not an embedded-only vector-database feature.

Use mature SQLite persistence through `Microsoft.Data.Sqlite`. Dependency/version and native packaging details remain subject to the repository's normal dependency, security, licensing, and packaging review during implementation.

## Current-state catch-up baseline

At implementation start, SQL Server is the reference baseline. 1.18A must inventory the repository's actual current persistence state rather than relying on an older roadmap snapshot.

The baseline is determined from:

- `HiveDatabaseSchema.CurrentSchemaVersion` and all migration scripts present at implementation start;
- every concrete SQL-backed persistence store currently used by the service graph;
- the Management contracts those stores implement;
- all durable resource/state capabilities already present in completed/current project work.

At the current documentation checkpoint, the repository schema is version **15**, and the SQL persistence surface includes Provider resources, AgentDefinition, WorkItem, event/snapshot/outbox persistence, structured-extraction persistence, ExecutionTarget favorites, Base-Agent durable work state, and the Hive Secret Store. Any additional SQL-backed durable capability added before 1.18A implementation begins is automatically part of the catch-up baseline.

The current SQL Server behavior is preserved as the regression reference. 1.18A must not implement only the capabilities that happened to exist when this plan was originally written.

## Sequential implementation slices

These six slices are the implementation order for the single 1.18A phase. They are intentionally separated at the highest-risk responsibility boundaries without splitting the capability into multiple roadmap phases.

### Slice 1 — Backend-Neutral Persistence Boundary

Establish the authoritative backend-aware persistence configuration and composition boundary while preserving the existing SQL Server behavior. Define backend selection, backend-appropriate validation, immutable effective configuration snapshots, and the construction boundary needed for multiple persistence implementations. SQL Server remains the known-good implementation throughout this slice; Embedded is not activated merely because its configuration shape exists.

**Verification gate:** configuration load/save/validation works for both profiles; SQL Server graph construction/regression behavior remains intact; no backend-specific storage details leak into Core or Management contracts.

### Slice 2 — Embedded Persistence Foundation

Implement the Embedded relational storage foundation using SQLite through Microsoft.Data.Sqlite, including application-owned local storage, connection/lifecycle handling, schema/version management, ordered deterministic migrations, initialization, reopen/recovery behavior, and storage-path/security/error boundaries. This slice establishes the reusable Embedded persistence substrate before full contract parity is built on top of it.

**Verification gate:** clean initialization, schema/version behavior, reopen/recovery, corruption/incompatibility handling, path/permission failures, locking/busy behavior, rollback, cancellation, and disposal boundaries are verified without claiming full parity yet.

### Slice 3 — Embedded Persistence Parity

Implement the Embedded backend for the **complete current SQL Server-backed durable persistence surface** identified by the catch-up baseline. This includes all applicable current resource/state stores, event/snapshot/outbox state, structured-extraction state, Base-Agent durable work state, favorites, provider completion/pricing/usage records where durable, and Hive Secret Store persistence. Preserve the same logical contracts, identities, ownership/scope, provenance, lifecycle, concurrency/versioning, deterministic ordering, cancellation, and error semantics.

**Verification gate:** shared behavioral coverage demonstrates SQL Server and Embedded satisfy the same applicable persistence contracts; representative end-to-end durable scenarios persist/reload correctly; SQL Server remains regression-safe.

### Slice 4 — Full-Data Migration

Implement the Management-owned logical migration operation for both directions: SQL Server → Embedded and Embedded → SQL Server. This slice owns quiescence/preflight, clean-destination requirements, deterministic dependency-ordered transfer of **All Hive Data**, failure-safe/incomplete migration handling, source immutability, destination verification, migration identity/schema evidence, and Secret Store re-protection. Migration must not silently activate the destination.

**Verification gate:** both migration directions succeed on complete representative Hive datasets; identities, versions, relationships, lifecycle state, event/snapshot/outbox consistency, work state, and protected secrets are verified; invalid/non-empty/incomplete destinations and unquiescent sources are safely rejected.

### Slice 5 — Host Composition, Settings UI & First-Run Default

Wire the authoritative persistence configuration into host/application composition, safe candidate-graph replacement, and the existing Persistence Settings surface. Implement the Database Setup / Data Migration tabs, backend selector, backend-specific fields/status/lifecycle actions, and Management-only migration/configuration operations. The Persistence UI uses a discoverable SQL Server instance picker with a final `Custom...` choice, a Browse action for Embedded storage locations, compact grouped rows for Server / Port, SQL credentials, and Connection Security / Command Timeout, and footer status/action placement. Data Migration keeps Direction + Scope together at the top and always shows Destination on the left and Source on the right, swapping backend roles without leaving large direction-dependent disabled sections. Implement the intended normal end-user first-run default of Embedded while preserving developer/test LocalDB as SQL Server-based.

**Verification gate:** the real host can configure both backends without bypassing Management, failed candidate composition leaves the existing graph intact, backend selection does not implicitly migrate or activate anything, and the intended end-user Embedded first-run behavior is manually verified.

### Slice 6 — Cross-Backend Hardening, Full Regression & Closure

Exercise and harden the complete 1.18A result across both persistence profiles. This includes cross-runtime/restart/crash recovery, concurrency/versioning, cancellation/disposal, migration round-trips in both directions, security/redaction boundaries, SQL Server regression coverage, Example Host coverage, full documentation closure, and final developer verification.

**Verification gate:** all six slice boundaries are satisfied, the complete SQL Server ↔ Embedded migration paths are verified in both directions, the required Example Host scenario is manually verified, the broader automated suite passes, and 1.18A is only then recorded complete.

### Sequential-slice rules

- Only one 1.18A slice is implementation-active at a time.
- A later slice must not begin before the previous slice's required developer verification succeeds.
- A failure in a slice returns only that same slice to `VERIFICATION FAILED / REMEDIATION REQUIRED` and then `VERIFICATION PENDING`; it does not authorize the next slice.
- A slice may touch multiple projects when required by its bounded responsibility, but it must not implement later-slice capabilities early.
- The six slices are not six independent roadmap phases. 1.18A remains one phase and closes only after Slice 6 completes.
- No parallel SQL and Embedded feature implementations are created above the persistence contract boundary; higher-level behavior remains shared.

## Scope

### 1. Backend-aware persistence contract

Extend the existing authoritative `HivePersistenceConfiguration` contract so the selected backend is represented explicitly without introducing a second configuration model.

The contract must support:

- `SqlServer` as the existing server profile;
- `Embedded` as the local profile;
- backend-appropriate configuration fields;
- the existing lifecycle/initialization policy semantics;
- immutable effective configuration snapshots for running operations.

SQL Server-only settings must not become required fields for Embedded mode. Embedded settings must not leak into SQL Server connection construction.

The existing management boundary remains authoritative: `Hive.Management` owns configuration/application operations; `Hive.Persistence` owns backend-specific construction, initialization, schema/migration execution, and persistence failures; the UI consumes Management contracts only.

### 2. Embedded relational persistence

Implement the Embedded backend for the durable Hive state in the current catch-up baseline, not merely the older set named in the initial 1.18 roadmap.

The implementation must cover the persistence contracts currently backed by SQL-specific stores, including where applicable:

- Provider;
- ProviderAccount;
- ExecutionTarget;
- ExecutionTarget preferences/favorites;
- AgentDefinition;
- WorkItem;
- durable events and snapshots;
- outbox state;
- structured-extraction persistence;
- Base-Agent durable work state;
- the durable Hive Secret Store/resource-credential persistence already owned by the selected persistence boundary;
- any other SQL-backed durable Hive resource store already defined by completed V1 slices, without moving the external JSON application-configuration store or SQL bootstrap credential store into the embedded database.

The embedded backend must preserve the existing logical contracts, identifiers, ownership/scope, provenance, lifecycle, concurrency/versioning, deterministic ordering, cancellation, and error semantics. It must not introduce an embedded-specific resource type or change the authority model.

### 3. Schema, initialization, and migration

Embedded persistence must have an explicit schema/migration lifecycle equivalent in intent to the current SQL Server boundary.

Required behavior:

- clean local store can be initialized explicitly by Hive;
- schema version is authoritative and bounded;
- migrations are ordered and deterministic;
- failed migration does not report success or advance the logical schema version;
- future/incompatible schema is rejected before normal use;
- reopen after clean shutdown works;
- reopen after process termination/crash preserves committed durable state;
- partial/incomplete local storage is reported as a typed persistence failure rather than silently replaced.

The implementation may use SQLite-native transaction/locking primitives, but callers remain backend-neutral.

### 4. Persistence storage location and security

Embedded mode needs one explicit, application-owned storage location.

The location is configuration, not a hidden per-feature database path. Hive must not create unrelated database files per resource family.

The implementation must establish the local-file lifecycle, directory creation, access-denied handling, invalid-location handling, and safe reopen semantics.

Hive resource secrets must continue to use the existing Secret Store contract. Embedded persistence does not make plaintext secrets acceptable merely because the database is local.

The SQL bootstrap credential boundary remains SQL-specific. Embedded mode must not require or create a SQL bootstrap credential.

The implementation must preserve the existing rule that credential material is not emitted into ordinary configuration, diagnostics, Example output, or migration metadata.

### 4.1 Complete bidirectional Hive-data migration

1.18A must provide one Management-owned logical migration operation with two directions:

`SQL Server → Embedded`
`Embedded → SQL Server`

The migration scope is fixed to **All Hive Data**. There is no partial resource-family migration in this slice.

The source and destination are selected persistence backends, but migration does not copy backend-specific database files, SQL tables, SQLite pages, migration journals, or other physical storage artifacts. It reads the authoritative Hive logical records from the source boundary and writes those records through the destination boundary.

The transferred dataset includes every Hive-owned durable record represented by the current 1.18A catch-up baseline, including:

- Provider / ProviderAccount / ExecutionTarget state and relationships;
- ExecutionTarget preference/favorite state;
- AgentDefinition state;
- WorkItem state and immutable attachments;
- Questions/Answers and other Base-Agent durable work state;
- event history, current snapshots, and outbox state;
- structured-extraction persistence;
- provider completion/pricing/usage records where they are currently durable;
- Hive Secret Store records and their protected secret material;
- any additional Hive-owned durable persistence record added before 1.18A implementation starts.

Stable identities, resource versions, ownership/scope, provenance, lifecycle state, timestamps, and relationships must be preserved. The migration must not silently assign replacement identities or reset versions.

The destination must be initialized to the supported destination schema before logical data import. A destination that already contains Hive logical data is rejected in 1.18A; migration is not merge or overwrite functionality.

Migration must run from a **quiescent source**. New persistence mutations, active execution persistence, and outbox dispatch must be stopped or drained before the source dataset is read. If the source cannot be quiesced safely, migration fails preflight rather than copying a moving dataset.

Migration is failure-safe:

1. validate source and destination;
2. establish the destination schema/current compatibility;
3. begin the destination migration boundary;
4. transfer logical records in deterministic dependency order;
5. verify identities, relationships, versions, lifecycle state, counts, and all required durable record families;
6. mark the destination migration complete only after verification succeeds.

If the destination cannot provide one transaction over the complete dataset, it must maintain an explicit incomplete-migration state that blocks normal activation until the migration finishes and verification succeeds. A failed or cancelled migration must never be presented as a usable complete destination. The migration result must record enough source/destination identity and schema information to establish exactly which source state was transferred.

The source remains unchanged by migration. A successful migration does not automatically switch the active Hive backend; backend activation is a separate explicit Settings operation.

Secret migration must resolve source secrets through the existing `ISecretStore` contract and pass protected `SecretMaterial` into the destination Secret Store so the destination re-protects the material. SQL/Embedded-specific ciphertext is not treated as portable data. If a source secret cannot be resolved under the authorized current security context, migration must fail rather than silently omit that secret record; re-entry/reprovisioning belongs to an explicit recovery path, not silent data loss.

The SQL bootstrap credential is outside the Hive database and is not migrated. When the destination is SQL Server with SQL-password authentication, its bootstrap credential must be provisioned separately.

### 5. Host composition and lifecycle

The host composition root must select the persistence backend from the authoritative configuration instead of hard-coding the SQL graph.

The application-level lifecycle is:

`load settings → validate candidate configuration → construct complete candidate backend graph → construct Management facade → publish candidate graph → dispose old graph`

A failed candidate construction must leave the currently published graph intact.

Changing only Provider/ProviderAccount/ExecutionTarget/AgentDefinition configuration must continue to use Management reads and refresh behavior without rebuilding the persistence graph.

Running operations use the already-established effective configuration/resource snapshots and are not silently retargeted by a later backend-setting change.

Changing the selected backend in Database Setup is **not** a data migration operation. A backend selection change must not implicitly copy, transform, merge, or delete data. 1.18A separately provides an explicit Data Migration operation for moving the complete Hive-owned dataset between SQL Server and Embedded.

### 6. Settings UI

Use the existing Hive Persistence Settings page. Do not create a separate persistence window and do not create a Vector Database settings page.

The Persistence page uses the existing `HiveTabControl` and contains:

`[ Database Setup ] [ Data Migration ]`

The Database Setup and Data Migration surfaces are full-width workspaces inside their tab pages. The UI uses the shared Hive visual foundation with structured sections, consistent label-above-input field blocks, responsive two-column grouping where the fields are naturally paired, and a footer status/action bar. It does not rely on a collection of unrelated fixed-height editor rows.

#### Database Setup

The Database Setup tab contains:

`Backend: [Embedded | SQL Server]`

Embedded mode shows only the fields relevant to the embedded profile, organized as an Embedded Storage section centered on the application-owned database file, Browse action, initialization policy, and command timeout.

SQL Server mode retains the existing server/instance, port, authentication, database, security, and initialization settings. The Server / port control is a dedicated Hive SQL Server instance picker: it combines SQL-client network enumeration with the installed local SQL Server instance inventory, de-duplicates results, normalizes installed local instances to `localhost` / `localhost\\<Instance>`, keeps `Custom...` as the final choice, and reveals a free-form server/instance field when Custom is selected.

#### Data Migration

The Data Migration tab supports both directions:

`SQL Server → Embedded`
`Embedded → SQL Server`

Migration scope is fixed to **All Hive Data**. The tab presents source and destination status/configuration, destination preflight validation, bounded progress/status, and final verification. Partial resource-family migration, merge behavior, destructive overwrite, and live synchronization are not supported.

The UI must:

- use existing Hive UI foundation controls/layouts;
- consume Management configuration/readiness/initialization and full-data migration operations;
- avoid constructing SQLite/SQL Server connections directly;
- avoid exposing secrets or raw connection strings;
- keep readiness/testing distinct from initialization/migration where the backend supports both concepts;
- preserve non-destructive behavior for tests and explicit lifecycle behavior for initialization/migration.

The backend selector changes the configuration being edited; it must not silently replace the active runtime graph until the host/application applies the new configuration successfully.

A successful migration also must not silently activate the destination backend. The source remains active until the user explicitly selects and applies the verified destination configuration.

### 7. SQL Server compatibility

The SQL Server profile remains a supported first-class backend and must not be degraded by the embedded implementation.

The implementation should preserve:

- current SQL configuration shape and security boundaries;
- SQL bootstrap credential behavior where applicable;
- existing DbUp schema/migration behavior;
- existing SQL persistence stores and tests unless shared backend-neutral contracts require a bounded change;
- existing developer LocalDB usage as a SQL Server development deployment.

Do not replace SQL Server with Embedded and do not make Embedded a prerequisite for SQL Server.

### 8. Failure, concurrency, and recovery requirements

The embedded backend must explicitly handle:

- cancellation;
- concurrent reads/writes within supported SQLite semantics;
- transaction rollback;
- disposal while operations are admitted/in-flight;
- locked/busy storage;
- malformed/corrupt/unreadable database files;
- permission and path failures;
- schema incompatibility;
- duplicate/conflicting resource writes;
- deterministic listing/ordering;
- restart/reopen;
- no cross-runtime leakage of uncommitted state.

The implementation should use the narrowest retry/timeout behavior compatible with SQLite's locking model. Unbounded retry loops are not allowed.

### 9. Tests

Add focused automated coverage in `Hive.Tests` for:

- configuration load/save with both backends;
- backend-specific validation;
- clean initialization;
- current SQL Server persistence-surface parity for the Embedded backend;
- migration success/failure and schema version behavior;
- bidirectional SQL Server ↔ Embedded full-data migration;
- exact identity/version/relationship preservation during migration;
- dirty/non-empty destination rejection and incomplete-migration protection;
- persistence/reload across process/runtime recreation;
- transaction rollback;
- concurrency/versioning boundaries;
- deterministic listing/order;
- cancellation;
- malformed/unreadable/locked storage failures;
- ownership/scope isolation;
- Secret Store migration/re-protection and SQL bootstrap credential non-migration;
- host candidate-graph failure isolation;
- regression coverage proving SQL Server remains supported;
- coverage that later application behavior consumes backend-neutral contracts rather than duplicating SQL-vs-Embedded feature logic.

Where the same persistence contract is implemented twice, shared behavioral tests should be reused through a test-side abstraction rather than copied with divergent expectations.

### 10. Example and manual verification

Add a focused `Hive.Example.WinForms` scenario under the existing Persistence settings/example area that demonstrates:

- Database Setup → selecting Embedded;
- initializing the local store;
- showing backend/storage status without revealing secrets;
- creating or loading representative current durable Hive state;
- closing/restarting the runtime and observing the same durable state;
- Data Migration → SQL Server → Embedded;
- verifying the complete transferred dataset, including identities/relationships and protected secrets;
- Data Migration → Embedded → SQL Server;
- verifying the complete reverse transfer;
- explicitly activating the verified destination;
- preserving the existing SQL Server configuration path without introducing a second logical model.

The example must remain a consumer of public Management/persistence contracts and must not construct a competing SQLite or SQL Server service graph.

Required handoff format:

`Example to run: <exact Persistence / ... scenario> — Hive.Example.WinForms`

`Tests to run: <exact focused Hive.Tests class/file>; broader-suite requirement if applicable`

Manual verification must include first-run Embedded initialization, normal reopen, persistence after restart, the Database Setup and Data Migration tabs, both migration directions, complete-data verification, failed/preflight migration behavior, explicit post-migration backend activation, and confirmation that existing SQL Server configuration continues to work.

### 11. Later-phase boundary

After 1.18A, later Hive phases consume the backend-neutral persistence contracts established by this phase and its completed slices. A later phase must not duplicate its feature/application logic for SQL Server and Embedded. Backend-specific storage work belongs inside the persistence implementation of the contract being consumed.

## 12. Default deployment behavior

A normal new end-user installation is intended to default to Embedded so Hive can run without an externally installed database server. The existing developer/test `LocalDevelopment()` / LocalDB helpers remain SQL Server-based unless deliberately changed by a future repository decision.

The default change is not considered implemented merely because it is documented; 1.18A must implement and manually verify the actual first-run behavior before recording completion.

## Explicit non-goals

- no vector insertion/search/indexing; 1.19 owns vector implementations after Embedded persistence is complete;
- no unrelated redesign of the existing SQL Server persistence implementation;
- no semantic memory, Knowledge, Wiki, Skills, Learning, Dream, Mistake/Success, or other CognitiveAgent semantics;
- no distributed synchronization between SQL Server and Embedded;
- no live bidirectional SQL↔Embedded synchronization;
- no merge, partial-family, or destructive-overwrite migration;
- no configuration package import/export (Phase 8 owns that broader portability capability);
- no second Hive resource model;
- no arbitrary/custom database-engine implementation;
- no requirement to install or configure a database server for Embedded mode;
- no unverified claim that an end-user installation defaults to Embedded; 1.18A must implement and manually verify that first-run behavior before recording it as complete.

## Completion boundary

1.18A is complete only when **all six sequential slices have reached their verification gates** and the Embedded backend has caught up to the **current SQL Server-backed Hive persistence surface at implementation time**, the existing SQL Server backend remains supported and regression-safe, both backends are selected through one authoritative configuration/composition boundary, the Persistence Settings page exposes Database Setup and Data Migration, complete bidirectional SQL Server ↔ Embedded migration transfers and verifies all Hive-owned durable data, restart/crash/security/concurrency boundaries are tested, the Example Host scenario is manually verified, the intended end-user Embedded first-run behavior is verified, and developer verification is recorded.

Completion of 1.18A does not close or pre-implement 1.19. Vector retrieval remains the next vector-specific slice and must separately add bounded `IVectorStore` implementations for both persistence profiles.
