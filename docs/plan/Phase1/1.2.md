# 1.2 — Secret Store

## Purpose

Establish Hive's credential-storage boundary so provider secrets can be referenced safely by configuration without exposing secret material through normal resource models, diagnostics, or configuration files.

## Scope

- Implement the Hive ISecretStore contract with the approved DPAPI-backed storage boundary.
- Store secret material encrypted at rest using the user-scoped Windows protection mechanism.
- Return stable secret references/descriptors rather than placing plaintext credentials in ProviderAccount or other durable configuration objects.
- Support secure replacement and deletion.
- Ensure replacing a credential invalidates the previously stored secret for subsequent resolution.
- Keep secret resolution behind the owning Management/resource boundary rather than exposing secret material broadly.
- Redact secrets from diagnostics, provider-test output, logs, and ordinary configuration views.

## Architecture boundary

The Secret Store is a credential boundary, not a general configuration store and not an authorization system. Provider configuration records a secret reference; provider operations resolve it through the established Management/Secret Store path.

Hive intentionally does not introduce an external secrets-vault architecture in V1.

## Non-goals

No plaintext persistence, secret values in repository examples, secret exposure through public resource DTOs, or provider-specific credential storage is allowed. This slice does not redesign provider/account resources.

## Verify

Verify creation, resolution through the authorized boundary, replacement, deletion, invalidation of the previous credential, encryption-at-rest behavior, missing-secret handling, and redaction across diagnostics and provider-related output.
