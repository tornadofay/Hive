# 1.28 — Full-Pipeline Crash/Resume

## Purpose

Prove that the complete V1 workflow can recover safely across process termination and restart, preserving durable work identity and avoiding duplicate consequential host mutation.

## Scope

Recovery must cover the complete established workflow, including:

- WorkItem creation and lifecycle;
- Agent runtime/execution state;
- durable Base-Agent work state;
- input preparation and structured candidate state;
- Tool/policy/authorization and human-intervention state where applicable;
- business-operation attempt state;
- business-operation receipt;
- reconciliation of unknown or partial host outcomes;
- multiple-Agent assignment state introduced by Phase 1.27;
- Review state and terminal Review outcomes.

The recovery model must use durable Hive state as the restart anchor. Runtime and process-local objects may disappear and be reconstructed.

Representative crash checkpoints include:

- after WorkItem creation but before execution;
- during provider execution;
- after durable operation-attempt creation but before the host receives the mutation;
- after host submission but before Hive receives the response;
- after host submission/receipt but before reconciliation is committed;
- between Agent/WorkItem completion stages;
- while Review is pending;
- during multiple-Agent concurrent processing.

On restart, recoverable WorkItems and Agents resume or reconcile according to their durable state. Already-terminal work must not be treated as new work.

## Safety and consistency rules

- A single WorkItem retains its stable identity through restart.
- Logical business-operation identity remains stable across retry/reconciliation where the host boundary supports idempotency.
- A non-idempotent host operation must be reconciled against authoritative host state before Hive attempts a second mutation after an unknown outcome.
- A known successful host mutation is not repeated merely because the Hive process terminated before persisting the corresponding terminal state.
- Failure of one WorkItem or Agent must not incorrectly fail unrelated work.
- Durable Base-Agent state remains isolated by Agent/runtime/resource scope.
- Receipts remain attributable to the WorkItem that caused the operation.
- Review state survives restart and remains distinct from approval and execution status.
- Recovery remains cancellation-aware, bounded, authorized, and consistent with existing provider/resource governance.

## Architecture boundary

MAF framework checkpoint/resume behavior is used where MAF already owns the applicable mechanism. Hive owns the durable WorkItem/resource identity, authorization, host-operation attempt/receipt/reconciliation semantics, Base-Agent persistent state, Review state, and recovery rules that extend beyond MAF.

This slice proves recovery across the assembled V1 workflow; it does not create a second workflow engine.

## Non-goals

No new Agent generation, persistent Hive membership model, Swarm resource, cognitive lifecycle, or alternate persistence/recovery architecture is introduced.

## Verify

Use deterministic fault-injection or process-termination coverage at multiple checkpoints. After restart, verify:

- no duplicate terminal host mutation;
- recoverable work resumes or reconciles correctly;
- already-terminal WorkItems remain terminal;
- unrelated WorkItems/Agents continue independently;
- durable Base-Agent work state is consistent;
- receipts and Review state survive restart;
- unknown/partial host outcomes are reconciled before unsafe retry;
- cancellation and authorization remain enforced during recovery.
